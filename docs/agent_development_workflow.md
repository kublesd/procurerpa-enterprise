# Agent 专题：开发、验证与交接流程

## 什么时候读

每个修改任务开始和结束时阅读；只回答问题、不修改文件时可只执行相关的只读调查。

本文只负责通用开发流程、验证选择、授权边界和证据格式。当前任务由 [`../PROGRESS.md`](../PROGRESS.md) 唯一声明；能力边界见 [`procurement_completion_gap.md`](procurement_completion_gap.md)；S1～S9 的历史阶段契约见 [`procurement_rpa_development_guide.md`](procurement_rpa_development_guide.md)。

## 开始前

1. 执行 `git status --short`，记录并避开无关修改。
2. 阅读 `AGENTS.md`、`PROGRESS.md` 和 `DECISIONS.md`。
3. 确认 `PROGRESS.md` 是否存在明确活动任务；没有时不得从历史路线自行领取工作。
4. 写一句完成定义，并列出范围内、范围外、验收条件和停止条件。
5. 只读取一份最相关专题文档、真实调用方和代表性测试。
6. 用 `rg` 查定义、注册点、路由、迁移和调用方；文件存在不等于已接入运行链。

首次安装或依赖变化时，使用仓库现有入口：

```text
make setup
make test
```

Windows 没有 GNU Make 时运行对应的 `python -m pip install -e ".[dev]"` 与 `python -m pytest tests -q`。前端依赖和命令以 `skyvern-frontend/package.json` 为准。不要在文档中维护第二套脚本事实。

## 有界实现

- 只编辑完成定义所需文件；发现必要的新文件或新责任时先说明并扩大范围。
- 先让最小业务规则成立，再接数据库、权限、审计、Skyvern 和 UI；不要为未来工作预建抽象或配置。
- 复用已有 helper、dependency、模型和测试模式。新增依赖前证明标准库和现有依赖不足。
- 修共享逻辑前检查全部真实调用方；API 变更同时检查前端调用与响应字段。
- 数据模型变更同时更新 Alembic，并验证 Model、迁移图和至少一个真实数据库路径。
- 外部依赖不可用时可以用 mock 验证局部逻辑，但必须把真实联调记为未验证。
- 无关失败只记录，不顺带修复；达到完成门或范围/风险边界后立即停止。

## 授权边界

任务中的本地修改授权通常包含相关只读调查、测试、lint、编译、触及文件格式化和已批准状态文档更新，但不自动包含以下动作：

- commit、push、分支创建/切换、PR、发布或部署；
- 生产环境、远程服务、外部系统或真实供应商写入；
- 读取或传递密钥、Token、密码及其他凭据；
- 删除、覆盖、强制重写历史、数据库 downgrade 或其他难恢复操作；
- 超出已批准文件或业务目标的实现。

这些动作必须获得单独明确授权。任何授权都不能放宽 [`agent_security_rules.md`](agent_security_rules.md) 的数据和采购决定边界。

## 最小验证矩阵

| 改动范围 | 必跑 | 条件式验证 |
| --- | --- | --- |
| 文档/AGENTS | 本地链接检查、批准文件边界、`git diff --check` | harness validator |
| Python 纯逻辑 | 对应 `tests/unit/test_*.py` | `ruff check` 当前文件 |
| API/权限 | 路由测试 + 同组织/跨组织负例 | PostgreSQL 集成测试 |
| SQLAlchemy/迁移 | 模型测试 + `alembic heads` | 真实 `upgrade head` |
| Skyvern 调用链 | 相关单元/集成测试 | Compose smoke |
| 前端 | 对应 Vitest | `npm run build` |
| Compose/配置 | `docker compose config` | health + SIT |
| 金额/安全 | 专项正反例 | 脱敏日志人工抽查 |

优先调用 `Makefile` 已有目标；只运行与当前修改及其依赖风险有关的命令。计划中的命令、历史成功或 mock 结果不能写成本次通过。

## 完成与阻塞

任务完成需要同时满足：

- 范围内行为和可观察验收条件成立；
- 最小相关验证实际通过；
- 真实、模拟、未接入和未验证边界明确；
- 没有敏感信息泄露、跨租户行为或真实采购主链回归；
- 未验证项、失败、保留债务和下一动作已记录；
- 工作区只包含已批准修改和开始前已有的无关修改。

遇到新凭据、生产/外部写入、破坏性操作、重大架构选择或无法证明的权限来源时停止并请求唯一必要决定。普通技术困难不是阻塞；先穷尽安全的只读调查、局部测试和可逆替代方案。

## 失败与恢复记录

对于 Compose、迁移、浏览器、LLM 或外部依赖失败，至少记录：

1. 第一个可操作的失败信号和安全错误类型；
2. 已保留的数据库、Task、Artifact、Review 或缓存状态；
3. 重试是否安全、是否幂等，以及最多重试到何处；
4. 已完成的恢复或清理；
5. 下一步需要的命令、环境变化或用户决定。

不得反复修改外部状态来试探成功，也不得把先前版本的成功覆盖到当前未验证实现上。

## 状态与证据

- `PROGRESS.md`：当前目标、活动任务、最新观察、阻塞、下一步和仍影响后续工作的债务。
- `DECISIONS.md`：影响后续工作的重大选择、原因、否决方案和约束；不记录可从代码直接推导的细节。
- `summaries/`：已关闭阶段的详细历史证据；不决定当前任务。
- 路线、架构、安全和历史实施指南：提供边界与背景；不保存动态分支、当前迁移 head 或下一任务。

证据记录必须包含：

```markdown
- 来源：本次直接观察 / 用户报告 / 历史记录。
- 修订与环境：`<git rev-parse HEAD>`；`<主机/容器/外部服务>`。
- 命令或检查：`<实际执行内容>`。
- 结果：`<退出码、通过数、状态或安全证据 ID>`。
- 失败或未验证：`<原因>`。
- 恢复与保留状态：`<事实>`。
- 剩余验收差距：`<事实或无>`。
```

历史 commit ID 在仓库中不可解析时，明确标记为历史标签，不把它当作当前可复现 revision。

## 结束顺序

1. 运行最小验证和 `git diff --check`。
2. 核对 `git diff --name-only` 未超出批准路径。
3. 更新 `PROGRESS.md`；只有重大取舍才追加 `DECISIONS.md`。
4. 最终汇报修改文件、实际验证、未验证项、保留债务和停止原因。
5. 停止，不自动领取下一阶段、commit、push 或部署。
