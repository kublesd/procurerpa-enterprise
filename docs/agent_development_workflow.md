# Agent 专题：开发、验证与交接流程

## 什么时候读

每个编码任务开始和结束时阅读；只回答问题、不修改文件时无需执行全部流程。

本文把开发 Agent 的工作压缩成固定顺序。来源/为什么：减少漏读调用方、过度修改和“没验证就完成”；适用条件：历史 Day 与当前 P1～P6 功能对等阶段；过期条件：仓库采用同等明确的自动化任务系统。

## 首次运行

```bash
make setup && make test
```

执行指令来源/为什么：统一依赖安装和后端基线；适用条件：首次进入仓库或依赖文件变化；过期条件：Makefile 被新的唯一入口替换。

Windows 没有 `make` 时使用等价命令：

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m pytest tests -q
```

替代指令来源/为什么：Windows 默认环境可能没有 GNU Make；适用条件：`make` 命令不存在；过期条件：开发环境统一提供 Make。

前端任务首次运行还需要：

```bash
cd skyvern-frontend
npm ci
npm test
```

前端安装指令来源/为什么：根 `setup` 只安装 Python 开发依赖；适用条件：修改 TS/TSX、CSS 或前端 API 类型；过期条件：根 setup 接管前端依赖。

## 开始前五步

| 步骤 | 指令 | 来源/为什么 | 适用条件 | 过期条件 |
| ---: | --- | --- | --- | --- |
| 1 | `git status --short` | 保护用户和其他 Agent 的修改 | 每个任务 | 独立临时工作树 |
| 2 | 读任务、AGENTS 和一个相关专题文档 | 控制上下文与范围 | 每个任务 | 入口机制替换 |
| 3 | `rg` 查真实调用方、路由、模型、迁移和测试 | 文件存在不代表已接通 | 后端/接口任务 | 自动调用图门禁 |
| 4 | 写一句完成定义和最小验证命令 | 防止边做边扩大 | 非平凡任务 | 任务系统强制提供 |
| 5 | 只编辑完成定义所需文件 | 避免无关重构 | 所有修改 | 用户明确扩大范围 |

## 实现顺序

先判断当前任务属于哪个阶段：

**第一阶段（P1～P6 功能对等）：**

1. 核对 ProcureRPA 对应文件和当前采购术语。
2. 直接改最小 schema、Prompt、模板或演示契约。
3. 用现有单元测试、fake page、内存 store、模拟 handler 或短脚本证明采购行为。
4. 标记 `real/demo/simulated/not_connected`，记录第二阶段债务后停止。

**第二阶段（单项真实化债务）：**

1. 先让业务规则单独成立。
2. 再接数据库、服务端权限和审计。
3. 再接 Skyvern Task/Workflow/Action 或已有真实调用方。
4. 最后接前端、迁移兼容和真实 SIT。

阶段来源/为什么：当前目标先取得 ProcureRPA 采购化功能对等，不能用持久化或真实 Skyvern 接线提前阻断；适用条件：所有新能力；过期条件：P1～P6 全部完成且项目正式切入第二阶段。

## 修改规则

| 指令 | 来源/为什么 | 适用条件 | 过期条件 |
| --- | --- | --- | --- |
| 先复用已有 helper、dependency、模型和测试模式 | 减少重复实现 | 写新代码前 | 旧实现经验证不适用 |
| 新依赖前证明标准库和现有依赖不够 | 避免安装与维护成本 | 修改依赖文件时 | 用户明确指定依赖 |
| 数据模型变更同时更新 Alembic 和最小 PostgreSQL 检查 | SQLite/mocks 不能证明迁移可用 | 改 SQLAlchemy 模型 | 使用自动迁移生成与验证 |
| API 变更同时查前端调用和 response 字段 | 当前存在字段口径错位 | 改 endpoint/schema | 自动生成类型 |
| 修 bug 时查共享函数的全部调用方 | 根因修复比每个入口打补丁更小 | 修复共用逻辑 | 函数只有一个调用方 |
| 外部依赖不可用时用 Mock 验逻辑，但明确未联调 | 不让环境阻塞局部开发，也不制造已验证声明 | LLM/MinIO/Webhook 不可用 | 真实联调完成 |
| 遇到无关失败只记录，不顺带修 | 保持任务可审查 | 失败与当前 diff 无调用关系 | 用户另开任务 |

## 最小验证矩阵

| 改动范围 | 必跑 | 条件式验证 |
| --- | --- | --- |
| 文档/AGENTS | 链接、行数、`git diff --check` | Makefile 命令 `make -n` |
| 第一阶段功能对等 | 对应上游单元测试或一个最小 demo | 相关模块联合演示；不强制 Compose/Skyvern |
| Python 纯逻辑 | 对应 `tests/unit/test_*.py` | `ruff check` 当前文件 |
| API/权限 | 对应路由测试 + 同/跨组织用例 | PostgreSQL 集成测试 |
| SQLAlchemy/迁移 | 模型测试 + `alembic heads` | 离线 SQL 或真实 upgrade |
| Skyvern 调用链 | 当前单元/集成测试 | Compose smoke |
| 前端 | 对应 Vitest | `npm run build` |
| Compose/配置 | `docker compose config` | health + SIT |
| 金额/安全 | 专项测试必须通过 | 日志人工抽查 |

矩阵来源/为什么：按风险选最小证据，不用全仓测试掩盖主链；适用条件：准备验收时；过期条件：CI 能可靠选择并执行同等检查。

## 常用命令

```bash
make test
python -m pytest tests/unit/test_risk_detector.py -q
python -m pytest tests/integration/test_day_2_postgres.py -q
alembic heads
docker compose config
docker compose exec skyvern python scripts/smoke_procurement.py
cd skyvern-frontend && npm test
cd skyvern-frontend && npm run build
```

只运行与当前修改有关的命令；P6 或第二阶段真实集成验收才运行相应联合矩阵。来源/为什么：节省反馈时间并遵守停止条件；适用条件：日常阶段开发；过期条件：CI 全量检查足够快且稳定。

## 完成与阻塞判断

任务完成需要同时满足：

- 当前阶段需求已经实现。
- 第一阶段：采购语义和最小演示成立，模拟/内存/未接入边界已标记；不要求进入真实调用链。
- 第二阶段：对应能力进入约定的真实数据库/Skyvern/权限/审计链，不再用 demo 证据代替。
- 最小相关验证通过，并记录实际命令和结果。
- 没有敏感信息泄露或对现有真实采购主链的回归。
- 未验证内容和第二阶段债务被明确写出。

以上完成条件来源/为什么：既避免把模拟能力宣传为生产能力，也避免旧真实链门槛阻断第一阶段直接适配；适用条件：准备宣告阶段完成；过期条件：用户给出更严格的完成定义。

只有同一阻塞条件连续确认且无法在当前权限与范围内解决时才向用户求助。来源/为什么：先穷尽安全、只读和局部替代方案；适用条件：缺少外部权限、密钥或关键业务选择；过期条件：阻塞解除。

## 状态持久化

`PROGRESS.md` 保存最新状态，`DECISIONS.md` 保存重要取舍；二者是跨会话事实源，不用聊天记录代替。

| 指令 | 来源/为什么 | 适用条件 | 过期条件 |
| --- | --- | --- | --- |
| 任务开始先读两个文件；内容与 Git 或代码冲突时以真实仓库为准 | 防止重复开发和继承过期结论 | 每个开发任务 | 状态由同等机制自动注入 |
| 验证完成后更新 PROGRESS 的 commit、测试、已完成、进行中、问题和下一步；未知项写“未验证” | 下一 Agent 需要最新且可核查的状态 | 每个任务结束 | 自动状态采集覆盖这些字段 |
| 重要架构选择才追加 DECISIONS，记录日期、原因、否决方案和约束；不重写历史，不记录可从代码直接推导的细节 | 保留取舍原因且控制文件体积 | 做出影响后续开发的选择 | 决策被正式 ADR 系统接管 |
写入顺序固定为“实现与验证 → PROGRESS → DECISIONS（如有）→ 可选阶段 summary”，确保状态不会先于真实结果。

## 阶段交接文档

历史 Day 12～16 summary 保留为采购真实主链档案，不再作为 P1～P6 的领取门。新功能对等阶段默认只更新短小的 `PROGRESS.md`；只有证据过长或用户要求时才新增：

```text
summaries/parity_pN_summary.md
summaries/parity_pN_code_list.md
```

`summary` 固定包含：

1. 做了什么：用业务语言写 3～6 条。
2. 真实调用链：从入口写到结果。
3. 设计决策：只写影响后续开发的选择。
4. 踩坑记录：只写实际遇到并解决的问题。
5. 验证结果：命令、通过数量或实际 smoke 证据。
6. 尚未验证：不要把 Mock 写成真实联调。
7. 后续建议：最多 1～3 个非阻塞项。

`code list` 固定包含：

1. 新增文件及业务作用。
2. 修改文件及业务作用。
3. 复用的已有入口。
4. 验证命令。
5. 明确不在本 Day 范围内的内容。

交接格式来源/为什么：详细证据按需下沉，根入口与 `PROGRESS.md` 保持短小；适用条件：单个 P 阶段证据无法在 PROGRESS 中简洁表达时；过期条件：自动化状态文件包含同等信息。
