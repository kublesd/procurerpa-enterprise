# Day 7 — 企业微信与钉钉通知

## 做了什么

- 高风险和严重风险的采购任务创建审批后，系统会自动发送审批通知，不再需要审批人一直刷新审批页面。
- 默认先发企业微信；如果企业微信发送失败，再改发钉钉。两个渠道都没有配置时会直接跳过，不影响采购任务和审批记录。
- 通知只包含审批编号、任务编号、所属部门、风险等级、处理时限和审批中心链接，不会发送采购描述、供应商账户或 Webhook Token。
- 相同的采购请求重复提交时，只创建并发送一次通知，避免审批人收到重复消息。
- 已准备好订单异常通知模板。当前项目还没有订单跟踪服务，等后续出现真实订单异常事件时可以直接接入。
- `.env` 已从 Git 跟踪中移除，但本地文件仍然保留。项目也不再默认启用没有 Key 的 Gemini，因此没有配置 LLM 时后端仍能正常启动。

## 通知是怎么发送的

1. 采购员创建任务，系统完成风险判断。
2. 如果结果是 `high` 或 `critical`，系统先把审批记录保存到数据库。
3. 接口立即返回“等待审批”，通知在响应之后发送，不会因为企业微信或钉钉超时而卡住审批创建。
4. 企业微信发送成功后流程结束；发送失败时再尝试钉钉。
5. 如果两个渠道都失败，系统只记录脱敏后的渠道、结果和错误类型，采购任务仍保持正常的待审批状态。

通知使用以下环境变量：

- `WECOM_WEBHOOK_URL`：企业微信群机器人地址，可选。
- `DINGTALK_WEBHOOK_URL`：钉钉群机器人地址，可选。
- `PROCUREMENT_APPROVAL_URL`：审批人点击通知后打开的审批中心地址。

## 为什么这样做

- 当前演示项目没有用户通知地址簿，所以先使用组织统一的群机器人，不额外建设接收人管理功能。
- 没有增加 Redis 重试队列，因为当前也没有负责消费队列的通知 worker。保留一个无人处理的队列没有实际作用，还可能把 Webhook Token 留在 Redis 中。
- Day 7 先记录简单、脱敏的发送结果；等 Day 8 接入统一审计时，再把通知结果写入数据库审计记录。

## 实际遇到的问题

- 原 ProcureRPA 通知代码虽然能单独测试，但没有接入采购或审批流程，实际创建审批时不会发送任何消息。
- 原来的重试数据包含完整 Webhook 地址，存在泄露 Token 的风险，因此本次直接删除了这条无效重试链。
- 原通知模板会发送风险原因、操作描述和截图地址，信息过多。采购版改成固定摘要，从入口上限制敏感采购数据进入通知。

## 验证结果

- Day 2～7 最小相关测试：`102 passed`。
- 已覆盖企业微信和钉钉正常发送、4xx/5xx、平台错误、超时以及企业微信失败后自动改发钉钉。
- 已验证高风险审批创建后会调度通知；重复请求不会重复通知；通知失败不会影响审批记录和采购任务状态。
- 已验证通知内容和错误日志不包含测试 Webhook Token，也不会接收供应商银行账户等敏感字段。
- Ruff、`git diff --check` 和 Docker Compose 配置检查通过。
- 没有配置 LLM Key 时，配置模块和 Forge 应用可以正常导入。
- `.env` 仍保留在本地，但 Git 已不再跟踪；仓库历史中没有提交过非空的 `GEMINI_API_KEY`。
- 未发现阻断采购主流程的问题。

## 尚未验证

- 本次没有配置真实的企业微信或钉钉机器人，实际网络发送尚未验证；Webhook 请求和完整调用链已通过 Mock 测试。
- 当前没有真实订单跟踪服务，因此订单异常通知只完成了模板，还没有业务调用方。
